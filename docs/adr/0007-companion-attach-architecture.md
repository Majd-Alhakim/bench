# ADR-0007: The companion attaches to the user's own sessions (plugin + native guard + managed limits)

- **Status:** Accepted (2026-10-26, Gate 6 decision 4a); proposed 2026-10-26 with the companion architecture ([SYSTEM-DESIGN](../architecture/companion/SYSTEM-DESIGN.md)).
- **Numbering:** CR-009 reserved ADR-0004/5/6 for the notch, so the companion ADRs start at 0007.
- **Date:** 2026-10-26
- **Amended 2026-10-26 (SP-H1):** the spike answered this ADR's open questions; see "SP-H1 findings" at the end. Verdict GO with limits: 72 / 72 injected faults blocked, PreToolUse p95 33 ms as Claude Code times it, the managed hook survived 33 / 33 lower-scope disables.

## Context
The 26 Oct pivot ships a **companion** for Claude Code sessions people already run, not the Agent SDK team app of ADR-0001. None of the existing spikes (S0-1, M8, SP-B1) tested this "attach" path: they ran agents inside our own SDK process. The pre-mortem's must-haves fix the shape: distribute as a Claude Code plugin, `onFailure: "block"`, limits that neither a repo nor the agent can switch off, a heartbeat, a canary per CLI release, status-line chaining, no credential reading.

Facts that decide it (pre-mortem trust F1, F14, F16; execution F12, F20, F25, F26, F30):
- Hooks fail **open** by default; `onFailure: "block"` (2.1.295+) closes command and http hooks, not `Stop`.
- Project settings can set `disableAllHooks` and switch off user hooks; **user, project and local settings can't disable managed hooks**.
- Managed settings on Windows: `C:\Program Files\ClaudeCode\managed-settings.json` or `HKLM\SOFTWARE\Policies\ClaudeCode` (admin to write); `HKCU\…\Policies` is user-writable and used only when no admin source exists.
- A user-scope plugin applies to the terminal, the desktop app's local sessions and VS Code.
- One `statusLine` per settings scope.
- An `http` hook to the app fails when the app is closed: open (unsafe) or, with `onFailure: "block"`, it blocks every session (bricking).

## Options
| | Limits hold with the app closed | A repo or the agent can switch them off | Bricks Claude Code if the app dies | Distribution |
|---|---|---|---|---|
| A. `http` hooks to the running app | ❌ | Yes (user scope) | **Yes** with `onFailure: block` | Plugin |
| B. Edit `~/.claude/settings.json` from outside | ✅ | Yes | No | None (pollutes user config) |
| **C. User-scope plugin calling a native guard exe + limits in admin-written managed settings** | ✅ | **No** (managed tier); limits left at user scope are labelled "not locked" (CR-010) | No: the guard is standalone; the app is optional | Plugin + one UAC step |
| D. Launcher (`claude --settings …` per session) | Only for sessions we launch | No for those | No | App (misses every other session) |

## Decision
**Option C.** Three independent layers, each useful alone:
1. **Limits (managed tier, one UAC prompt, D-4).** The four limits are **always on** and can never be switched off; per limit, the user chooses only whether it is **locked** with admin (this layer) or left at user scope, labelled "not locked" (CR-010, founder 2026-10-26). For the locked limits, an elevated helper writes our entries into the managed settings source (file or HKLM, whichever Claude Code reads on that build; merged, never overwriting an organisation's policy) and installs a **pinned limits-only guard** to `C:\Program Files\Eucas\limits\eucas-guard.exe` (admin-writable only). The managed entries are a `PreToolUse` + `PermissionRequest` hook to that exe with `onFailure: "block"`, plus `permissions.deny` patterns for the limits as a second layer that needs no binary at all. The app never sets `allowManagedHooksOnly` or `disableAllHooks`. Changing the locked set later asks for admin again, through the helper's fixed `update-locked-set` operation. **All four start ticked to lock in setup**; you can untick any (founder, 2026-10-26). **Locking your own rules** (D-4 as drawn in the approved CR-011 design: "Lock 4 limits + 4 rules"; **since 2026-10-26 setup locks only the four limits**, in its one UAC prompt before sign-in, and rules chosen in setup are written at user scope, "Not locked"; you lock a rule later from Rules, founder *"okay do that"*, SYSTEM-DESIGN §5.6): only **block** rules can be locked; `update-locked-set` then also takes a list of block rules validated against a strict schema (exact programs and arguments, or a folder scope for file tools; no allow rules, no globs, no free text), written as managed `permissions.deny` patterns. The worst a forged request can do through our UAC prompt is block more, never allow more (SECURITY-PRIVACY T7; confirm in BUILD-PLAN §6).
2. **Plugin (user scope, no admin).** The `eucas` plugin, which **carries the guard binary in its own `bin/`**. The installer writes it to a local marketplace folder (`%LOCALAPPDATA%\Eucas\marketplace\`); `claude plugin marketplace add` + `claude plugin install eucas@eucas --scope user` register it. ~~They copy it into Claude Code's plugin cache, so the guard never depends on the app folder.~~ **SP-H1: a directory marketplace runs the plugin in place from that folder**, so the marketplace folder is part of the install (finding 2 below). Hooks for heartbeat checks, user rules (auto-approve), needs-you, same-file, session lifecycle and the supervisor's `Stop` moments, all calling `eucas-guard.exe` in exec form. The plugin's guard enforces all four limits in every case. For each limit left not locked (or all four, if the user declines UAC), the same `permissions.deny` patterns go into the user's `~/.claude/settings.json` (recorded as a JSON patch, so "limits in your user settings" in the UI is literally true), and every surface labels that limit "not locked" (CR-010, founder 2026-10-26).
3. **App (per-user; the notch and its panel since CR-011, the tray as a fallback, ADR-0016).** Reads guard events, status-line JSON, `claude agents --json` (optional) and local transcripts (metadata only). It owns the UI, the heartbeat verdict, the tripwire, the retro, the rules editor, the canary and the diagnostic. **Closing or crashing the app weakens nothing in layers 1–2**; it stops the heartbeat display, notifications and the tripwire, and the quit dialog says so.

Status line: the plugin (or, if SP-H1 shows a plugin can't ship it, the user `settings.json` with a backup) points `statusLine` at `eucas-guard status-line`, which runs the user's saved command, prints its output byte for byte, and tees the JSON to the app. Uninstall restores the saved command exactly.

## Consequences
- The locked limits survive a closed app, a crashed app, a repo's `disableAllHooks`, an agent editing user settings, and a user-writable guard being replaced; limits left not locked survive a closed or crashed app, but a repo's `disableAllHooks` or an edit to user settings can weaken them (the heartbeat shows it), which is why they carry the label. They do not survive an admin or an organisation policy, which is correct.
- A limits guard that can't start blocks every session, and only an admin step lifts it: the helper's `repair` and `pause-limits` operations (one UAC prompt each), described in SYSTEM-DESIGN §7.1.
- Two guard copies with different update paths: the limits guard changes rarely and each change costs one UAC prompt (stated in release notes); the plugin guard updates freely.
- Org-managed PCs with `allowManagedHooksOnly` get the "Blocked by your organisation" state; we never write into an employer's policy.
- Cloud sessions load none of this (trust F44); the gap line says so.

## SP-H1 findings (2026-10-26)
1. **Exec form only.** Every hook, in the plugin and in managed settings, is `{ "command": "<exe>", "args": [...] }`. A shell-form hook breaks under `shell: "powershell"` (Claude Code rewrites `${CLAUDE_PLUGIN_ROOT}` into syntax PowerShell can't parse), and with `onFailure: "block"` that blocks **every** tool call. A contract test asserts that every hook in `hooks.json` and in our managed entries has `args` (TESTING §3.1).
2. **The plugin runs in place from the marketplace folder.** With a `directory` marketplace, `CLAUDE_PLUGIN_ROOT` is the marketplace folder, not the plugin cache, even though `claude plugin install` also copies it there. So layer 2's guard lives at `%LOCALAPPDATA%\Eucas\marketplace\eucas\<version>\bin\eucas-guard.exe`, and **the marketplace folder is part of the install**, not a staging area: deleting it makes every session fail closed (safe, and Repair rewrites it from the app's embedded copy). The sentence above ("copy it into Claude Code's plugin cache, so the guard never depends on the app folder") is **wrong for a directory source**; the guard still doesn't depend on the *app* folder, because `%LOCALAPPDATA%\Eucas\` and the app's install folder are separate. Updates write a **new versioned folder** and repoint the marketplace manifest, so a running session keeps the guard it loaded; old folders are removed only when no running session reports that plugin version (SYSTEM-DESIGN §7). A copied `git`/`url` source wasn't tested and isn't needed.
3. **A running session never picks up a newly installed plugin** (no hot load; `/reload-plugins` exists only in the TUI). Hooks written into a settings file **are** hot-reloaded within ~3 s, and so are managed entries. First run lists sessions that started before the install as "not protected until restarted".
4. **The plugin can't ship the main `statusLine`** (neither from its `settings.json` nor from `plugin.json`). The fallback above applies: user `settings.json`, with the saved command backed up and restored on uninstall.
5. **Both admin sources work:** the file (`C:\Program Files\ClaudeCode\managed-settings.json`) and the HKLM `Settings` value each enforced the hook alone, and both together. Which wins when they differ wasn't tested, so the helper **merges into whichever already exists and, if both exist, writes the same JSON to both**. `HKCU\…\Policies` is never used. `CLAUDE_CODE_MANAGED_SETTINGS_PATH` is ignored outside Anthropic's eval harness, so it isn't a bypass.
6. **User-scope limits are detectable, not enforceable.** Deny rules held Edit, Write, shell redirects and `Add-Content` on `~/.claude/settings.json`, but `node -e "fs.writeFileSync(…)"` got through; any interpreter can. That confirms why a lock lives in the managed tier, and the "not locked" label stays honest. Detection rule (heartbeat): a `config-change` event, a session with transcript activity but no `session-start` / `check` events, or a tool_use without a matching check → "not protected" within the heartbeat window.
7. **Hosts are identified by image path, not name:** the desktop app's main process, its bundled CLI and a terminal CLI are all `claude.exe`.
